# Breaking changes

This is the running log of breaking changes in glissade, and the policy that
governs them while the project is pre-1.0. It is normative; the rationale lives
in [`docs/DESIGN.md`](docs/DESIGN.md) §7.4 and §8.

## Pre-1.0 versioning policy (`0.x`)

- **All packages move in lockstep.** Every `@glissade/*` package and the unscoped
  `glissade` umbrella share one version number, bumped together by changesets
  (the `fixed` group in `.changeset/config.json`). You never mix versions across
  the set.
- **In `0.x`, a *minor* bump (`0.MINOR.0`) may contain breaking changes.** This is
  the standard npm semver convention for pre-1.0 software: the leading `0` means
  the public API is not yet frozen, so breaking changes ride a minor bump, not a
  major one.
- **A *patch* bump (`0.x.PATCH`) is safe** — bug fixes and additive, backward-
  compatible changes only. Upgrading a patch should never require code changes.
- Until `1.0`, prefer pinning a minor (`~0.x.0`) if you need to avoid surprise
  API churn, and read this file plus the changelog before taking a minor bump.

## Stricter promises: the two versioned document schemas

Two on-disk formats are versioned **independently of the code API** and carry a
stronger stability promise, because breaking them orphans users' files:

- **The Timeline document** (`version` field — the interchange format, DESIGN §2.3).
- **The SidecarDoc** (`sidecarVersion` field — the studio editor's persistence
  layer, DESIGN §6.2).

A change to either ships with a migration (so old files keep loading), and is
called out explicitly in this log. We treat silently breaking a serialized
document as a release-blocking regression.

## How breaking changes are announced

1. **A changeset entry** (`.changeset/*.md`) describes the change and, for a
   breaking one, marks it as such — this is what produces the version bump and
   the per-package `CHANGELOG.md`.
2. **An entry in the log below**, with the version it landed in, what broke, and
   the migration path (a manual note, or a codemod once `@glissade/codemod`
   exists — planned once `studio` has users, DESIGN §7.4).
3. The package `CHANGELOG.md` files (generated by changesets) remain the
   authoritative per-release detail; this file is the curated, breaking-only view.
